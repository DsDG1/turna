## 二、三项固有限制(修 bug 消不掉,需要显式决策)

### ① 引擎生命周期耦合
单一事实源 = 单引擎 = 单生命周期闸门。视图收敛、决策写入、物理删除、GC 全部排队等引擎打开。
本夜实证:10 万卡的物理删除在账本 retiring 后**等了数小时**,直到用户下一次导入碰巧打开引擎才执行(collection 100001→4700)。
真实用户生活里「复习必开引擎」所以大概率会收敛——但收敛时机是概率性的,不是保证的。这不是 bug,是架构选择。

### ② 共享 collection 上的来源所有权
v1 靠内容复制天然隔离每个导入;v2 所有 source 共享一个 collection,note 以 GUID 全局去重。
于是必须回答 v1 从不需要回答的问题:同一包重导(笔记被「更新」而非新建)时所有权归谁?两个包含相同 GUID 的卡归谁?
本夜的 F5 是这个问题的第一次暴露。receipt 语义(new+updated+duplicate+conflicting 并集)只是数据面,策略面(接受转移?拒绝并明示?)缺失。

### ③ 双代并存的乘法效应
每个「这段课程/来源/卡归谁」的 v1 解析面都需要一条 v2 分叉。B6 接了 4 个读挂点,本夜又发现 2 个遗漏(删除 owner 解析、课时正文装载)。
这不是 v2 的缺陷,是迁移策略的成本;**Step 6 拆掉 v1 后此项整体消失**。风险在 Step 4→6 期间:每个遗漏的挂点在这期间都是不可用路径。

## 三、结论

**问题主体是可修的具体缺陷**:F3/F4/F6 分别是夹具/接线/未建件问题,逐项修复即可消除;F1/F2 的机制已被契约兜住。写侧(导入→账本→视图→删除收敛)经真机证明成立,含硬性能实证(10 万卡 commit 3.5s、视图重建 2.8s、强杀零数据损伤)。

**三项固有限制需要显式决策,不是修 bug 能消的**:
1. 限制① 二选一:启动时见 v2 active 源即主动开引擎(收敛变保证);或接受概率收敛并把它写进设计文档(含用户可见后果)
2. 限制② 定一条重导/同 GUID 策略(拒绝+明确 UI,或所有权转移规则),写进 ADR
3. 限制③ 不动架构,只改「v2 完成」的定义:以真机冒烟绿为准

## 四、流程教训(一句话)

step4 收据曾把「课程树由视图生成」记为完成——依据是 host 测试绿;真机首夜证明最基本的用户流(进一个课时)从未通过。
**假引擎测试验证不了接线;完成标志以真机冒烟为准,host 绿只是必要条件,不是完成证据。**
